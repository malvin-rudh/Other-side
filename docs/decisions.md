# Decisions

## 2026-10-08: Shell, context store, i18n foundation

- **Context key format** (`src/engine/context.ts`): `ticker|session|cutoff|periodStart..periodEnd|scenario|locale|dataVersion|taxonomyVersion|claimVersion`, with `none` for unset fields. Pure function of the analytical slice, so the key is deterministic and testable. Field order fixed; version bumps to the key change it (locale and versions are part of the key per project rules).
- **Fields kept out of the context key**: `briefDate` is a UI-only Brief-screen selection and never enters analytical calculations or the key; `demoMode` is an auth/import flag, also not analytical. Both are plain store fields updated without recomputing the key (tested).
- **`dataThrough` added to the store** alongside the mandated fields: the header badge "data through {date}" needs the data-coverage date, which is manifest metadata, not an analytical input, so it is stored but excluded from the key.
- **Manifest versions**: `npm run build:data` writes `public/data/manifest.json` (dataVersion, taxonomyVersion, claimVersion, dataThrough = last captured session), and `App.tsx` loads it through `applyManifest`, which patches the versions into the analytical context and sets `dataThrough`. A missing or invalid manifest leaves versions untouched; `applyManifest(null)` is a no-op.
- **Store defaults**: ticker `SINI` (the prototype ticker), scenario `default`, locale `en`, all dates `null`. `setTicker` normalises to upper case; `setPeriod` rejects an inverted range.
- **Response acceptance**: `isCurrentResponse(expectedContextKey, latestRequestId, response)` accepts only when both match; `createRequestId()` uses `crypto.randomUUID()`. Async callers own their latest-request bookkeeping; the pure helper is unit-tested for the stale-context and superseded-request cases.
- **i18n**: `en.json` is the typed source of truth (`Messages`), `id.json` must match its key set (enforced by a Vitest parity test). Missing keys fall back to English, then to the key itself. Dates render via `Intl.DateTimeFormat` in `en-GB`/`id-ID`, UTC-parsed, so session dates never shift by viewer timezone.
- **Shell**: bottom nav (Brief/Stock/Method) below `md`, inline header nav at `md+`; the historical badge hides below 480px to keep the 390px header uncluttered. Orange (`#F58220`) reserved for active/primary states.

## 2026-10-08: Normalized SINI public data build

- **Repeatable build**: `npm run build:data` runs `scripts/build-data.ts` with `tsx` and regenerates all public data from `data/raw/*`; outputs contain no wall-clock timestamps.
- **Stable accepted row IDs**: accepted broker-summary rows use `SINI-YYYYMMDD-BNN` / `SINI-YYYYMMDD-SNN`. Raw import identity stays separate under each row's `source` object with source file, source line and raw labels; absent source IDs/frequency are not fabricated.
- **Integer parser**: `parseSafeIntegerLabel` supports suffix labels such as `1,1B` and `1,6K`, rejects unsafe/fractional values, and rounds values within `0.001` of an integer to absorb floating-point artifacts already present in the CSV while preserving the raw label.
- **13 Aug quarantine**: all 44 raw rows on 2026-08-13 are excluded from accepted rows and listed in validation diagnostics; duplicate ranks and broker-days on both sides remain visible in `validation.json` rather than silently netted.
- **Conflict handling**: outside quarantine, duplicate ranks or a broker-day appearing on both sides reject the later row without overwriting the earlier accepted row. The current source has zero non-quarantined rejects after safe integer normalization.
- **Sessions**: `sessions.json` spans 2026-08-13 through 2026-09-23 and explicitly distinguishes excluded, captured, missing, holiday and weekend dates. 8 Sep is missing; 17 and 25 Aug are holidays.
- **Broker profiles**: group mapping is code-driven (XL/XC/YP app-facing; AK/BK/ZP/YU/AI/DP/TP institution-facing; known others other/mixed; unknown codes unknown). YP receives the same treatment as other brokers: app-facing group, Weak profile strength because no citation is available.
- **Evidence sources**: profile evidence uses team mapping as basis and `pending` source reference where no citation exists; broker profile notes explicitly say the profile does not establish customer identity in both languages.
- **Event availability**: raw event dates are treated as publication dates per the raw file note; `availableAt` is `publicationDateT00:00:00+07:00`. The helper `isEventAvailableAtCutoff` gates on `availableAt`, not event/reporting date.

## 2026-10-08: Flow and predicate engine

- **Signed magnitudes**: visible net-buy rows contribute positive lots/value and visible net-sell rows contribute negative lots/value. Inputs, sums and multiplications are checked with `Number.isSafeInteger`.
- **Windowing**: all flow aggregates require an explicit inclusive `{ start, end }` window; invalid inverted windows throw rather than silently swapping dates.
- **Scenario grouping**: base broker groups come from `public/data/brokers.json`; scenario overrides can move specific broker codes to `unknown` without changing residual visible net.
- **Residual**: `residual` is the total signed visible net across all groups in the window. It is not silently balanced to zero because top-nine visible rows are incomplete by design.
- **Implied references**: price references keep numerator and denominator and round only the display value. Missing row inputs return unavailable; zero denominator returns unavailable; unsafe numeric inputs return unavailable or throw depending on the aggregation path.
- **Cutoff rule**: session D rows become eligible at `D+1T00:00:00+07:00`; event visibility is publication/`availableAt` based.
- **Five-session predicates**: actual market sessions exclude holidays/weekends only. Missing or excluded required sessions produce `not_enough_data` instead of failing or passing a streak.
- **Main-buyer streak**: the candidate group must be positive and strictly larger than every other group including `unknown` for each required session.
- **Broker reversals**: reversal predicates report only opposite observed net directions through one broker and carry an explicit caveat that this is not a proven same-client round trip.

## 2026-10-08: Fact catalogue and approved-claims layer

- **Fact envelope**: every fact carries `fact_id` (`F-{ticker}-{key}-{compactStart}-{compactEnd}-{baseline|reference}`), catalogue key, type, period, `source_row_ids` / `source_event_ids` / `source_sessions`, a typed `value` union (integers, ratios with numerator+denominator, group nets, rankings, streaks, coverage, reversals, sensitivity, label evidence, events), unit, `approximate` display text, `coverage_note`, `available_at`, evidence strength + one-line reason, and the three versions. Display text and notes are bilingual (`{en, id}`) so both locales render identical numbers.
- **Unavailable means unsupported**: a fact that cannot be computed from visible data at the cutoff is emitted with `available: false`, `value: null`, a bilingual `unavailable_reason`, and evidence strength `Not enough data`, never guessed or zero-filled. C12/C13 return unavailable (not `fails`) when fewer than five required sessions exist.
- **Cutoff-clamped windows**: fact windows end at the last eligible market session ≤ cutoff, so a 24 Aug view contains no September data; every `available_at` is asserted ≤ cutoff in tests.
- **Reference facts**: `REF-INST-2SEP`, `REF-INST-CUTOFF` and `REF-XL-SELL` are first-class facts with their own periods and row-level traceability (matched rows listed by ID), not display-only numbers.
- **Claims**: 23 claims in five sections (observed / interpretation / unknown / supports / contradicts) reference only catalogue facts through a small predicate language (`fact_available`, `fact_status`, `fact_bool`, comparison on a numeric fact with optional group focus, `all`/`any`/`not`). A claim is offered to the model only when all its fact dependencies are available and its predicate holds, so e.g. on 24 Aug the C13 wording is unavailable while C12 is allowed, and the institution-thesis supports/contradicts claims flip on 23 Sep.
- **Wording and caveats live in templates**: `src/ai/templates.ts` holds reviewed bilingual short/explained wordings, a caveat key set, and curated questions. Claims carry caveat keys resolved to bilingual text at build time; locale changes never alter claim IDs, predicates, signs or caveats.
- **One validator**: `validateModelResponse` in `src/ai/validate.ts` is the single pipeline for live answers, saved answers and Method-page tests: Ajv shape (closed schemas) → answer_kind consistency → context-key + request-ID match → duplicate/unknown claim IDs → per-claim availability at cutoff → dependency `available_at` ≤ cutoff (kills future references) → follow-up IDs must be curated questions.

## 2026-10-08: Stock screen (/stock/SINI, P05)

- **Versions derived from loaded public docs**: the Stock screen builds its context versions from `sessions.json` (`dataVersion`), `brokers.json` (`version`) and `events.json` (`version`) after Ajv validation in `loadPublicData`, so the screen stays correct even if the manifest fetch fails; the built `manifest.json` feeds `applyManifest` for the store context and header badge.
- **Cutoff derived from the selected session**: the screen never stores a cutoff; `cutoffAt = sessionAvailableAt(selectedSessionDate)` (D+1 00:00 WIB) inside the view memo, so the replay cutoff always matches the session the user picked.
- **Effective window clamped for display**: `buildStockView.effectiveWindow` ends at the last eligible market session ≤ cutoff even when the period extends past it (e.g. period to 23 Sep viewed from 24 Aug shows a 14–24 Aug window), keeping chart axes, tooltips and the header period line free of future points.
- **Charts recompute from raw rows**: proxy and cumulative series are built with `dailyGroupNet` / `impliedPriceReference` over the clamped window rather than reading C-facts, so chart data is row-level and independently testable; a golden test ties the cumulative endpoint to the C04–C06 group nets.
- **Evidence buttons carry full fact IDs**: every on-screen number is an `EvidenceButton` whose `data-fact-id` is the fact's real `F-{ticker}-{key}-{period}-{variant}` ID (header proxy C10, group nets C04–C07, rankings C08/C09), so the P07 evidence drawer can resolve facts without a mapping table.
- **SSR component testing without testing-library**: `renderToStaticMarkup` + `vi.mock` on `usePublicData` and on the Zustand store module. Zustand v5's server snapshot calls `api.getInitialState()` on the internal vanilla api, a creation-time capture that `setState` cannot change and spies cannot reach (`Object.assign` copies the reference), so the mocked `useContextStore` hook reads a plain mutable object reset per test. Reuse this pattern for future screen tests.
- **Chart SSR guards**: Recharts `Tooltip` formatter accepts `unknown` with a typeof guard, and `ReferenceDot` renders only when the selected proxy is non-null, so server-rendered charts stay valid strict-TS markup.

## 2026-10-08: Session scrubber and changed strip (P06)

- **Timeline is a pure marker model**: `buildSessionTimeline` maps `sessions.json` to sorted `captured | holiday | excluded | missing` markers (weekends omitted entirely) plus a `capturedDates` list; prev/next navigation (`previousCapturedDate` / `nextCapturedDate`) steps only between captured sessions, never onto a grey or holiday date.
- **Native range input as the scrubber**: the slider is a native `<input type="range">` over the captured-session index, which gives arrow-key stepping, `aria-valuetext` with the formatted selected date and small-screen resilience for free (`min-w-0 flex-1` inside a wrapping flex row; the marker strip scrolls horizontally with `overflow-x-auto`). Quick stops (24 Aug, 3 Sep, 23 Sep) are plain buttons; Play advances one captured session per second via a 1 s interval that reads the selected date from a ref, and stops at the last session.
- **Grey markers explain, they never navigate**: 13 Aug (excluded) and 8 Sep (missing) render as dashed grey buttons whose title/aria-label carry the raw session `reason` verbatim; clicking opens a bilingual note (date, status, raw reason, method explanation). Holidays are non-interactive labelled dots. Changing the selected date clears the open note (and will clear evidence/AI state in P07) so nothing stale survives a date change.
- **Changed strip derives from C25 only**: `buildChangedStrip` reads the C25 `daily-group-nets` fact, names the previous and selected captured session dates, and lists up to three group moves (`CHANGED_MAX_LINES = 3`) sorted by absolute delta, excluding unchanged groups. When C25 is unavailable (first captured session) the strip renders an explicit "no previous session" note instead of invented moves.
- **ICU month-abbreviation variance in tests**: this environment's en-GB renders September as "Sept" while other ICU builds render "Sep"; screen tests match September dates with `/Sep(t)?/` rather than exact substrings (August is unaffected).
- **390px verification note**: the acceptance check "stepping is smooth at 390px" needs a live browser; the Qoder Browser Connector had no connected browser at implementation time, so responsiveness is verified structurally (wrapping control row, scrollable marker strip) but a manual 390px pass is still owed.

## 2026-10-09: Saved-answer generator script

- **scripts/generate-saved-answers.ts rebuilds the live context per item**: for each review date (24 Aug, 3 Sep, 23 Sep) and each registered thesis it constructs the same FactsContext the stock screen uses (default window, default scenario, cutoff at D+1 00:00 WIB) and runs buildFacts plus buildApprovedClaims, so a 24 Aug prompt can never contain a 23 Sep fact bundle; it sends one Qwen call per item with the bounded curated question, the claim registry with availability flags and the request ID to echo, then accepts the answer only if the existing validateModelResponse passes, and writes `{meta, contextKey, response}` files to public/data/sini/ai/{date}/{thesisId}.json with question ID, context versions, model ID, generation time and token usage.

## 2026-10-09: Server-only live Qwen adapter behind POST /api/explain

- **One prompt builder is shared by generator and server**: src/ai/plannerPrompt.ts `buildPlannerPrompt` is a verbatim extraction of the generator prompt, and scripts/generate-saved-answers.ts now delegates to it, so a saved plan and a live plan for the same context are planned from byte-identical prompts; the server only adds the optional "Thesis under test" line when thesis_id is present.
- **The handler is platform-neutral Request in, Response out**: server/explain.ts rebuilds the cutoff (D+1 00:00 WIB), facts and approved claims from the bundled public data on every call, rejects any body key outside {ticker, date, scenario, locale, question, thesis_id} (so client facts, prompts and URLs are all BAD_REQUEST), caps the body at 8 KB and the question at 600 chars, compares the Bearer demo token in constant time, and makes exactly one provider call behind a hard abort timer (default 10 s, no retry loop); answers are the success envelope (request ID, context key, versions, mode, model ID, structured mode, generated time, usage, plan) or one safe code: UNAUTHORIZED 401, BAD_REQUEST 400, RATE_LIMITED 429, INSUFFICIENT_DATA 404, UPSTREAM_TIMEOUT 504, VALIDATION_REJECTED 502, LIVE_DISABLED 503.
- **Structured output is explicit or probed, never guessed**: server/qwen.ts pins QWEN_MODEL from env (default qwen-plus, international compatible-mode base URL) and sends the exported responseSchema as a strict json_schema response_format; QWEN_STRUCTURED_MODE=json_object forces JSON Object mode, and an empty value probes json_schema then json_object once at startup, disabling live with an honest log line when neither is accepted; the upstream key lives only in process.env, is sent only in the Authorization header, and error messages never echo upstream bodies.
- **Blocked on account access, not faked**: the pinned model version and the structured-output probe could not be verified against a real Alibaba Cloud Model Studio account because no QWEN_API_KEY is available in this environment; local tests (server/qwen.test.ts, server/explain.test.ts, 28 cases with a mocked provider covering 401, bad input, live disabled, timeout with abort, rejected plan and success) and the build pass, and the probe-vs-pin verification is deferred to deployment with credentials.

An answer fetched at 15:58 WIB carries today's bar with values still moving, and reading that same answer at 16:02 found its session end in the past, so a pre-close bar became a completed close and could report a move that had not happened. Both recommended defences are in place. PriceSeries now carries observedAtMs, taken from the answer's own fetchedAt for provider series and null for fixtures (a fixture is historical by construction, so the cutoff rule alone governs it), and eligibleBars requires a bar's session end to be at or before the observation instant as well as at or before the cutoff. The gate therefore applies to holdings and to the benchmark, on fresh responses and on cache hits, and nothing but a fresh observation taken after the close can make a bar final. In addition the provider tracker excludes unfinished sessions before caching, so a cached answer cannot hold a pre-close bar at all; it applies to every adapter because it sits in the tracker rather than in the Yahoo parser.
